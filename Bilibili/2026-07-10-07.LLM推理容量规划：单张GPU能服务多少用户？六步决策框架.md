## 概述

从模型权重到每百万 token 成本，完整推导单 GPU 的容量规划。覆盖 KV Cache 计算、GQA 优化、SLO 延迟约束、吞吐量与成本对比。

> [!abstract] 六步决策框架
> 每个部署决策遵循同一条流水线：
>
> ```
> 权重显存 → 可用 VRAM → 最大并发用户 → SLO 延迟检查 → 吞吐量 → 成本
> ```

---

## 第一步：权重显存计算

模型权重显存大小 = 参数量 × 每参数字节数。精度一旦选定，权重显存就固定了。

| 模型 | FP16 | INT8 | INT4 |
|------|------|------|------|
| **Mistral 7B** | 14 GB | 7 GB | 3.5 GB |
| **70B 模型** | 140 GB | 70 GB | 35 GB |

> [!tip] 核心要点
> 这个数字一旦选定模型和精度就固定了。

---

## 第二步：可用 VRAM（KV Cache 预算）

GPU 显存不是全给权重，需要扣除约 **10%** 的框架开销和激活值。

**以 A10G 24GB 跑 Mistral 7B 为例：**

```
总显存：        80 GB  （A100 80GB 示例）
减去权重：     -14 GB  （Mistral 7B FP16）
减去开销：      -8 GB  （框架开销 + 激活值，约 10%）
────────────────────────
KV Cache 预算： 58 GB  ← 这就是服务用户的预算
```

> [!warning] 注意
> A10G 只有 24GB，跑不了 70B 模型。

---

## 第三步：最大并发用户数（GQA 优化）

每个用户的对话占用 KV Cache。Mistral 使用 **GQA（Grouped Query Attention）** 技术，只有 **8 个 KV 头**而非 32 个，KV 内存减少 **4 倍**。

### 计算过程

| 参数 | 值 |
|------|-----|
| 每 token KV 大小 | 131 KB |
| 上下文长度 | 4096 token |
| 每用户 KV 占用 | 131 KB × 4096 ≈ **537 MB** |
| KV Cache 预算 | 58 GB |
| **最大并发用户** | 58 GB ÷ 537 MB ≈ **107 个** |

> [!important] 内存天花板
> 这是内存上限，与 GPU 速度无关。

---

## 第四步：SLO 延迟检查

即使内存允许 107 个用户，实际并发越多，每个 token 生成越慢。每个 decode 步骤需要读取**所有权重 + 所有活跃 KV Cache**。

| Batch Size | ITL（Inter-Token Latency） | 用户体验 |
|-----------:|--------------------------:|---------|
| 80 | ~20ms | 达到 SLO 上限 |
| 170 | ~28ms | 用户体验卡顿 |

> [!danger] 实际限制
> 实际并发上限 = **min(内存上限, SLO 上限)**
>
> 内存允许 107 个，但 SLO 限制 batch=80 时 ITL 已达上限，所以**实际只能服务约 80 个并发用户**。

---

## 第五步：吞吐量计算

```
吞吐量 = batch_size × 1000 / ITL(毫秒)
```

**以 batch=80, ITL=20ms 为例：**

```
每步产出：80 token
每秒步数：1000 / 20 = 50 步/秒
吞吐量：  80 × 50 = 4000 token/秒
```

> [!note] 吞吐量平台效应
> 更多用户意味着更多 token 每步，但 ITL 也增长，导致步数减少。**吞吐量最终趋于平台期**。

---

## 第六步：成本对比

```
每百万 token 成本 = GPU 时薪 / (吞吐量 × 278)
```

| GPU | 吞吐量 | 时薪 | 每百万 token 成本 | 说明 |
|-----|-------:|-----:|-----------------:|------|
| **A10G** | - | - | **$0.20** | 最便宜，但跑不了大模型 |
| **A100** | 4000 t/s | $3.50/h | **$0.24** | 性价比均衡 |
| **H100** | 6667 t/s | - | **$0.23** | 吞吐量最高 |

> [!success] 关键洞察
> 选 GPU 不是越大越好——**选满足模型和 SLO 的最便宜选项**。

---

## 水平扩展

### 多副本扩展

```
总容量 = 每副本用户数 × 副本数

80 用户 × 10 张 GPU = 800 并发用户
```

负载均衡分发请求，**线性扩展**。

### 张量并行

模型放不下时采用张量并行，但有 **5-15% 的通信开销**。

---

## 公式速查表

| 步骤 | 公式 |
|------|------|
| **1. 权重显存** | 参数量 × 每参数字节数 |
| **2. 可用 VRAM** | 总显存 - 权重 - 框架开销（~10%） |
| **3. 最大用户数** | KV Cache 预算 ÷ (每 token KV × 上下文长度) |
| **4. 实际限制** | min(内存上限, SLO 上限) |
| **5. 吞吐量** | batch_size × 1000 / ITL(ms) |
| **6. 成本** | GPU 时薪 / (吞吐量 × 278) |

## 四大核心 Takeaways

| # | 要点 | 说明 |
|---|------|------|
| **1** | **六步决策框架** | 模型精度 → 权重显存 → 可用 VRAM → 最大用户 → 延迟检查 → 最终配置 |
| **2** | **内存决定上限，SLO 决定实际上限** | 两者取最小值 |
| **3** | **GQA 将 KV 内存减少 4 倍** | 直接放大并发用户数 |
| **4** | **选 GPU 不是越大越好** | 选满足模型和 SLO 的最便宜选项 |
