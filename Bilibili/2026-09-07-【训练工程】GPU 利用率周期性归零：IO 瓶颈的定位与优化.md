## 简介

训练时 GPU 利用率忽高忽低？周期性归零？训练速度远低于预期？大概率不是 GPU 的问题，是数据喂料跟不上——IO 瓶颈。

一、为什么 GPU 利用率忽高忽低：GPU 算完一个 batch 的梯度后，需要等下一个 batch 的数据。如果数据加载速度快，GPU 几乎不停歇，利用率高；如果数据加载慢，GPU 算完一个 batch 后要等几百毫秒甚至几秒等数据，这段时间利用率归零。周期性的利用率归零就是典型的 IO 瓶颈。
二、根因一，数据预处理太慢：很多数据集需要 tokenization、数据增强、动态 padding。如果这些操作在主线程里做，每个 batch 都要现算，速度极慢。解决方案是用 DataLoader 的 num_workers 参数开启多进程加载，让多个 CPU 进程并行预处理数据；同时用 pin_memory 把数据放到锁页内存，加速 CPU 到 GPU 的传输。
三、根因二，存储读取慢：如果训练数据放在 NFS 网络文件系统上，读取延迟可能高达几十毫秒。小文件多的情况更严重——几百万个 JSON 文件，每个几 KB，读取开销远大于数据本身。解决方案有三：第一，把数据预打包成大文件（比如 webdataset 或 HDF5），减少 IO 次数；第二，用 mmap 内存映射避免实际读取；第三，把数据预取到本地 SSD。
四、Alluxio 是一个专业的数据缓存方案：它在存储和 GPU 之间加一层缓存，把热点数据预取到 SSD 和内存里，GPU 直接从缓存读，不再等远程存储。知乎团队报告用 Alluxio 把 GPU 利用率从 60% 提升到 90%。对于大规模分布式训练，Alluxio 几乎是标配。
五、DataLoader 调参清单：num_workers 一般设为 GPU 数量的 2 到 4 倍，太少了数据加载跟不上，太多了进程切换开销大；pin_memory 设 True；prefetch_factor 设 2 到 4，让 DataLoader 提前准备好下一个 batch；persistent_workers 设 True，避免每个 epoch 重启 worker 进程。这四个参数调好，IO 瓶颈能大幅缓解。

一句话：GPU 假忙不是 GPU 的问题，是数据喂料跟不上。
