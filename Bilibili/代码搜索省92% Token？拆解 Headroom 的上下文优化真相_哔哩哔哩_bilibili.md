## 概述

使用 Claude Code 或 Cursor 等 AI 编程助手处理复杂项目时，Token 消耗极快。AI 读取的日志、工具输出和 RAG 检索结果中充斥着大量冗余信息。这不仅烧钱，还会带来**注意力稀释**和 **"Lost in the Middle"** 风险，让长上下文变成毒药。

Headroom 是一个开源的**本地上下文优化层**，官方基准中最高减少 **95%** Token 消耗，且未观察到明显准确率下降。

## 1. 长上下文的三大问题

| 问题 | 说明 | 后果 |
|------|------|------|
| **烧钱** | 日志、工具输出、RAG 结果中大量冗余 | Token 消耗像流水一样快 |
| **注意力稀释** | 关键信息被淹没在大量上下文中 | 模型注意力分散 |
| **Lost in the Middle** | 上下文中间位置的信息容易被忽略 | 准确率下降 |

> [!quote] 核心观点
> 长上下文不是越长越好，而是**越精准越好**。冗余信息会让长上下文变成毒药。

## 2. Headroom 是什么

> [!abstract] 定义
> Headroom 不是魔法压缩器，而是一个**本地上下文优化层**。

| 维度 | 说明 |
|------|------|
| **定位** | 上下文优化层（非单纯压缩） |
| **运行位置** | 本地，不依赖云端 |
| **压缩比** | 最高 60-95% |
| **准确率** | 官方基准中未观察到明显下降 |
| **兼容性** | 兼容所有主流 Agent |
| **开源** | GitHub 14K+ 星 |

## 3. 三阶段管线架构

Headroom 通过**三阶段管线**和**多个内容专用压缩器**实现优化：

```
原始上下文
    ↓
┌──────────────────────────────┐
│  Stage 1: 分析与分类          │
│  - 识别内容类型               │
│  - 区分代码/日志/文档/RAG等    │
│  - 标注重要程度               │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│  Stage 2: 专用压缩器处理       │
│  - 代码压缩器 (AST 感知)      │
│  - 日志压缩器 (模式提取)      │
│  - RAG 压缩器 (语义去重)      │
│  - 文档压缩器 (摘要提取)      │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│  Stage 3: 重组与输出          │
│  - 按重要性排序               │
│  - 保留关键上下文边界          │
│  - 输出优化后的上下文          │
└──────────────────────────────┘
               ↓
        优化后上下文
```

> [!tip] 专用压缩器的意义
> 不同于通用压缩工具的一刀切策略，Headroom 为不同类型内容匹配专用压缩器，这是其高压缩比且保持准确率的核心原因。

---

## 4. 内容专用压缩器

| 压缩器类型 | 处理对象 | 压缩策略 |
|-----------|---------|---------|
| **代码压缩器** | 源代码文件 | AST 语法树感知，保留结构语义，压缩注释和空白 |
| **日志压缩器** | 运行日志、错误输出 | 模式提取，去除重复日志行，保留关键错误信息 |
| **RAG 压缩器** | 检索增强结果 | 语义去重，合并相似片段，提取最相关内容 |
| **文档压缩器** | 文档、说明文件 | 摘要提取，保留关键 API 和用法说明 |

## 5. 与 Roofline 模型的关联

> [!note] 从算力成本角度看
> 结合[[Token为什么这么贵？前谷歌TPU架构师揭秘Token定价的物理极限]]的内容：
>
> - Token 定价受 **Roofline 模型**约束 — 计算瓶颈 vs 内存带宽瓶颈
> - **KV 缓存**是长上下文的主要内存消耗源
> - 减少 Token 数量 = 直接减少 KV 缓存大小 = 降低内存带宽需求 = 降低推理成本

## 6. 与 CodeGraph 的关联

> [!note] 从代码理解角度看
> 结合[[降低 57% Token 消耗！CodeGraph如何用本地图谱重塑 AI 编程]]的内容：
>
> - CodeGraph 用**本地图谱 + AST 语法树**减少 AI 需要读取的文件数量
> - Headroom 用**专用压缩器**减少每个文件送入的 Token 量
> - 两者思路互补：CodeGraph 解决"读哪些"，Headroom 解决"怎么读"
