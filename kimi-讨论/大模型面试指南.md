大模型 Agent 方向的面试，通常围绕 **理论基础、工程落地、系统设计、项目深挖** 四个维度展开。以下是核心准备方向及高频考点：

---

### 一、大模型基础（必考）

面试官会先确认你对底层原理的理解深度，不只是"调 API"。

| 方向                 | 关键内容                                                                     |
| ------------------ | ------------------------------------------------------------------------ |
| **Transformer 架构** | Self-Attention 计算复杂度、MQA/GQA 优化、位置编码（RoPE/ALiBi）、LayerNorm 前置/后置区别       |
| **预训练与对齐**         | Pre-training → SFT → RLHF/DPO 的完整链路；Reward Model 的构建逻辑；SFT 数据质量 vs 数量的权衡 |
| **长上下文**           | 外推技术（NTK-aware、YaRN）、上下文压缩（摘要、RAG）、LongRoPE 等                            |
| **模型选型**           | 不同参数规模模型的能力边界；什么场景用 7B、什么场景必须用 70B+                                      |

**高频题示例：**

- "为什么 LLM 会出现幻觉？从数据、训练、推理三个层面分析"
- "DPO 相比 PPO 的优势和劣势是什么？"
- "如果上下文超长（100k+），你会怎么优化推理成本和效果？"

---

### 二、Agent 核心架构（重点）

这是 Agent 岗区别于普通算法岗的核心。

#### 1\. 推理与规划（Planning）

- **CoT / ToT / GoT** ：思维链、思维树、思维图的原理与适用场景
- **ReAct** ：推理+行动交替的模式，为什么有效？缺陷是什么？
- **Reflection** ：自我反思机制如何设计？（如 Reflexion、Self-Refine）
- **多步规划** ：HuggingGPT、Plan-and-Solve 等范式

#### 2\. 工具调用（Tool Use）

- Function Calling 的实现原理（模型如何生成结构化参数）
- Tool Learning：模型如何学习使用新工具？（ToolBench、APIBench 相关思路）
- 工具选择策略：给定 100 个工具，如何快速路由到正确的几个？

#### 3\. 记忆机制（Memory）

- **短期记忆** ：对话历史管理（滑动窗口、Token 预算分配）
- **长期记忆** ：
	- 向量数据库（RAG）的选型与优化（Embedding 模型、分块策略、重排序）
		- 知识图谱作为记忆补充
		- 记忆总结与压缩（如 MemGPT 的虚拟上下文管理）

#### 4\. 多 Agent 协作

- **架构模式** ：层级式（MetaGPT）、平等协商式（AutoGen）、竞争/投票式
- **通信协议** ：Agent 之间如何交换信息？如何避免"互相甩锅"导致任务失败？
- **任务分解** ：如何将复杂任务拆解为子任务并分配给不同 Agent？

**高频题示例：**

- "设计一个能自动完成数据分析报告的 Agent，你会怎么设计它的 Memory 和 Planning 模块？"
- "ReAct 在某些任务上效果反而不如直接 Prompt，分析原因"
- "多 Agent 系统中，如果两个 Agent 的输出冲突，怎么解决？"

### 三、RAG 与知识增强（落地核心）

Agent 通常离不开外部知识，RAG 是面试重灾区。

| 模块 | 深挖点 |
| --- | --- |
| **文档解析** | PDF/图片/表格的解析方案；多模态文档如何处理？ |
| **Chunk 策略** | 固定长度 vs 语义分块；父子块、滑动窗口；Markdown/标题感知分块 |
| **Embedding** | 选型（BGE、M3E、OpenAI 等）；微调 Embedding 的场景和方法 |
| **检索优化** | 混合检索（向量+关键词+图谱）；Query 改写（HyDE、Step-back）；重排序（Cross-encoder） |
| **生成优化** | 上下文去重、冲突信息处理、引用溯源（Citation） |

**高频题示例：**

- "RAG 检索到了 10 个相关段落，但答案分散在不同段落里，怎么让模型生成连贯回答？"
- "如果知识库每天更新，如何保证 Embedding 的实时性？"
- "RAG 和 Fine-tuning 的边界在哪里？什么情况下选哪个？"

---

### 四、Prompt Engineering 与模型调优

- **结构化 Prompt** ：XML/YAML/JSON 格式对模型遵循指令的影响
- **Few-shot 设计** ：示例选择的策略（相似度、多样性、难度递进）
- **输出约束** ：JSON Mode、Regex 约束、Grammar-based Decoding
- **微调经验** ：LoRA/QLoRA 参数设置；数据构造技巧；Catastrophic Forgetting 的缓解

---

### 五、工程与系统设计

Agent 岗越来越强调 **端到端落地能力** 。

#### 1\. 系统架构设计

- 如何设计一个高可用的 Agent 服务？（异步任务队列、状态机、容错重试）
- 流式输出（SSE）的实现与前端对接
- 多轮对话的状态管理（Session、Context、Memory 的持久化）

#### 2\. 评估与监控

- **Agent 评估** ：不是简单看 BLEU/ROUGE，而是任务完成率、工具调用准确率、幻觉率
- **评估数据集构建** ：如何构造边界 Case（Corner Cases）？
- **线上监控** ：用户反馈闭环、Bad Case 归因分析

#### 3\. 安全与对齐

- Prompt Injection 的防御（输入过滤、输出校验、沙箱执行）
- 敏感信息脱敏、权限控制（Agent 能调哪些工具？能访问哪些数据？）

**高频题示例：**

- "设计一个客服 Agent，要求能处理退款、查询、投诉三类意图，画出系统架构图"
- "Agent 调用了一个写数据库的工具，怎么防止它误删数据？"
- "如何评估一个 Agent 的好坏？指标体系和评估方法？"

### 六、项目深挖（决定成败）

面试官会围绕你的项目经历追问细节，重点考察：

1. **问题定义** ：为什么选择 Agent 方案？不用传统 NLP/规则引擎的原因是什么？
2. **技术选型** ：为什么选这个模型？为什么用这个向量库？有没有对比实验？
3. **难点攻克** ：遇到过什么 Bad Case？怎么分析的？最终解决了多少？
4. **量化结果** ：准确率提升多少？延迟降低多少？用户满意度如何？
5. **迭代思路** ：如果给你更多资源，下一步优化什么？

**准备建议：** 每个项目准备 3 个 **有深度的技术细节** 和 1 个 **失败的教训/未解决的问题** 。

## 一、知识体系补强：4个必须补齐的短板

你的优势在小模型训练、SFT/DPO、数据工程；短板在 **Agent架构设计** 和 **系统视角** 。需要重点补以下四个方向：

### 1\. Agentic RAG（你的RAG经验升级）

你做过召回和rerank，但医疗场景的RAG正在从"检索-生成"升级为 **Agentic RAG** ——让Agent自主决定何时检索、检索什么、如何验证。

- **GraphRAG** ：ICD编码体系（ICD-10-CM/PCS）本身就是层级知识图谱，最新研究RAG-Coding将ICD表格列表编码为KG，让Agent在编码时进行 **知识图谱验证**
- **多跳推理** ：复杂病例需要跨文档推理（如从入院记录→出院记录→检验报告），Agent需要自主规划检索路径
- **结构化知识注入** ：不要直接扔原始文本给模型，而是像RAG-Coding那样，将编码指南蒸馏成 **代码特定的摘要** 供Agent调用

**面试考点** ：你会被问到"传统RAG和Agentic RAG在医疗场景的区别"，重点答 **自主决策能力** ——传统RAG是固定流程，Agentic RAG是模型自主决定是否需要二次检索、是否需要验证编码规则。

### 2\. Multi-Agent 协作架构（你的项目升级核心）

你的ICD编码、质控、病案首页生成，天然适合拆成多Agent协作。最新研究CLH（Code Like Humans）提出了模拟人类编码工作流的 **多Agent框架** ：

| Agent 角色 | 对应你现有工作 | 职责 |
| --- | --- | --- |
| **Evidence Extractor** | 医疗文本质控（信息提取） | 从病历中提取可编码的临床实体（诊断、手术、状态） |
| **Index Navigator** | 召回模型（语义检索） | 将实体映射到ICD字母顺序索引，召回候选编码 |
| **Tabular Validator** | 编码规则引擎 | 对照ICD表格列表和编码指南验证候选编码 |
| **Code Reconciler** | 病案首页生成 | 合并、排序、去重，生成最终编码集 |

另一个前沿方向是 **Agentic Auditing Automation** ：PLM-ICD（你的小模型经验）负责高召回候选生成，LLM Agent负责 **审计验证** ——这正是你"小模型+大模型"结合的优势点

**面试考点** ："如何设计一个多Agent编码系统，保证编码准确率和召回率的平衡？" 你要答出 **分工策略** （小模型做召回、大模型做验证）和 **冲突解决机制** （当编码Agent和质控Agent意见不一致时怎么办）。

### 3\. 医疗Agent的安全与可控性

医疗场景对幻觉零容忍。你需要体系化地准备：

- **幻觉分层防御** ：
	- 输入层：病历结构化校验（实体识别+医学术语归一化）
		- 推理层：CoT + 引用溯源（让Agent生成编码时标注依据文本片段）
		- 输出层：规则引擎硬约束（编码必须符合ICD-10-CM官方层级关系）
- **人在回路（HITL）** ：编码建议→人工确认→反馈优化，形成数据飞轮
- **责任追溯** ：每个编码决策需要可解释（为什么选这个编码？依据哪条指南？）

**面试考点** ："医疗Agent产生错误编码导致DRG分组错误，怎么追责和防控？" 这是考察你的 **工程风险意识** 。

### 4\. 数据工程 → Agent数据飞轮

你的"高质量数据筛选"经验在Agent时代价值极高，但需要升级叙事：

- **SFT数据构造** ：不是简单清洗，而是构造 **多轮工具调用轨迹** （ReAct格式：Thought → Action → Observation）
- **DPO数据构造** ：编码任务中，如何构造"好编码"vs"坏编码"的偏好对？（如：编码完整但过度编码 vs 编码精简但遗漏合并症）
- **Agent评估数据** ：需要构造边界Case（如：主要诊断选择争议、合并症 vs 并发症区分）

## 二、项目包装策略：把现有工作"Agent化"

你现有的三个业务方向，都可以包装成Agent项目：

### 项目1：ICD智能编码Agent（核心项目）

**原工作** ：小模型微调做ICD编码分类 → 大模型SFT做生成式编码

**Agent化包装** ：

> "我设计了一套 **多Agent协作的ICD编码系统** 。系统包含三个核心Agent：
> 
> 1. **编码Agent** ：基于SFT的大模型，负责从病历中抽取诊断实体并生成候选编码；
> 2. **验证Agent** ：调用ICD知识图谱和编码指南，对候选编码进行层级校验和规则校验（如性别冲突、年龄冲突）；
> 3. **审计Agent** ：对最终编码集进行完整性检查（如是否遗漏合并症、主要诊断选择是否合理）。
> 
> 技术亮点：我利用DPO优化了编码Agent的输出偏好，使其在'编码完整度'和'编码精确度'之间达到最佳平衡；验证Agent通过Function Calling对接内部规则引擎，实现编码的硬约束。"

### 项目2：病案文本质控Agent

**原工作** ：基于规则的质控 + 大模型辅助

**Agent化包装** ：

> "我将质控系统升级为 **Reflection-based Agent架构** 。质控Agent不仅检测病历缺陷，还具备 **自我反思能力** ——当检测到逻辑矛盾时，Agent会回溯病历上下文，定位矛盾根源，并生成修改建议。我通过构造'错误-反思-修正'的SFT数据，让模型学会了这种自我修正模式。"

### 项目3：病案首页生成Agent

**原工作** ：信息提取 + 模板填充

**Agent化包装** ：

> "病案首页生成是一个 **多步骤、多依赖的Agent工作流** 。我设计了状态机驱动的生成Agent：首先调用信息提取工具从多份病历中抽取关键字段，然后进入'编码Agent'生成ICD编码，再进入'质控Agent'校验首页逻辑一致性，最终输出结构化JSON。整个流程通过 **ReAct模式** 实现，Agent每步操作都有明确的Thought和Observation，确保生成过程可解释、可干预。"

## 三、模拟面试题（分难度层级）

以下题目结合你的医疗背景，按面试轮次设计：

### 一面：基础深度（考察知识扎实度）

**Q1：你做过SFT和DPO，在ICD编码任务中，DPO的偏好对怎么构造？**

- **期望答案** ：不只是"正确编码vs错误编码"，而是 **策略性偏好** 。例如：偏好对A——完整编码（含所有合并症）vs 精简编码（仅主要诊断）；偏好对B——遵循最新指南的编码 vs 遵循旧版指南的编码。Reward Model需要学会"在编码完整性和规范性之间权衡"。
- **加分点** ：提到DPO可能导致的 **偏好过度优化** （preference over-optimization）问题，以及如何用IPO（Identity Preference Optimization）或RSO缓解。

**Q2：医疗Agent调用工具时，如果模型生成了不存在的ICD编码（幻觉），你怎么在工程上拦截？**

- **期望答案** ：三层防御——① 输出层用ICD官方代码表做 **白名单校验** ；② 工具层让Agent通过Function Calling查询编码有效性， **不直接生成编码** ；③ 推理层用Constrained Decoding（如Outlines库）限制输出空间。

**Q3：你的召回模型（小模型）和大模型SFT在编码流程中是什么关系？**

- **期望答案** ：参考Agentic Auditing架构——小模型负责 **高召回的候选编码生成** （利用其模式识别能力和低延迟），大模型Agent负责 **上下文验证和精细选择** （利用其推理能力）。两者通过 **候选集传递** 协作，而非串行替代。

### 二面：项目深挖（考察问题解决能力）

**Q4：在你的ICD编码Agent中，如果编码Agent和质控Agent对同一个诊断的编码意见不一致，系统怎么裁决？**

- **期望答案** ：这不是简单的"听谁的"，而是设计 **置信度机制** 。编码Agent输出编码时附带置信度分数；质控Agent输出异议时也附带规则匹配度。系统设定仲裁策略：当两者冲突且置信度均高时， **降级为人类审核** （HITL）；当质控Agent基于硬规则（如性别冲突）提出异议时， **直接否决编码Agent** 。同时，将冲突Case记录到反馈库，用于后续DPO迭代。

**Q5：医疗病历很长（往往超过8k tokens），你的Agent怎么处理长上下文？**

- **期望答案** ：不要直接扔全文。采用 **分层摘要+按需检索** ——先让Agent读取病历结构（入院记录、出院记录、手术记录等），根据编码需求选择性深入。例如：编手术编码时，只精读手术记录和麻醉记录；编诊断编码时，重点看出院记录和病程记录。这本质上是Agent的 **注意力分配策略** 。

**Q6：你们的数据筛选流程具体怎么做？怎么保证筛选后的数据能提升Agent效果？**

- **期望答案** ：数据筛选不是"去重+去噪"这么简单。我采用 **能力导向筛选** ——先定义Agent需要的核心能力（如：实体识别能力、编码规则应用能力、长文本理解能力），然后针对每种能力构造评估集，筛选能增强该能力的训练样本。同时用 **数据混合策略** （data mixing）控制不同能力样本的比例，避免灾难性遗忘。

### 三面：架构设计（考察技术视野）

**Q7：设计一个支持100家医院并发使用的ICD编码Agent SaaS系统。**

- **关键考察点** ：
	- **多租户隔离** ：不同医院的病历数据、编码规则版本（ICD-10-CM/PCS版本可能不同）如何隔离？
		- **模型服务架构** ：Base模型共享，LoRA Adapter按医院/科室动态加载（Multi-LoRA Serving）
		- **知识库管理** ：各医院的本地化编码指南如何接入？用RAG还是微调？
		- **反馈闭环** ：各医院的审核结果如何安全地回流到模型优化？
		- **合规** ：数据不出院、审计日志、编码责任追溯

**Q8：如果让你带领一个5人小组做医疗Agent产品，你的技术路线怎么规划？**

- **期望答案** （体现技术判断力）：
	- **MVP阶段（0-3月）** ：单Agent + RAG，聚焦核心编码场景，快速验证PMF
		- **扩展阶段（3-6月）** ：引入多Agent协作（编码+质控），接入医院HIS系统
		- **深化阶段（6-12月）** ：构建数据飞轮（审核反馈→DPO迭代），探索Agent自主学习能力
		- **风险管控** ：始终保留人工审核节点，医疗安全优先于自动化率

**Q9：你怎么看目前LLM在ICD编码上的天花板？什么时候能完全替代人工编码员？**

- **期望答案** （体现行业认知）：参考最新综述观点——当前LLM更适合做 **编码辅助工具** 而非完全替代。天花板在于：① 编码需要完整病历上下文理解，LLM长上下文仍有局限；② 编码规则频繁更新（如ICD-10-CM每年更新），模型知识滞后；③ 医疗责任归属问题。未来3-5年应该是 **人机协作** 模式，Agent负责初编和质控，人工负责终审。

## 第二份：知识点面试题列表（按类别分类，真实有效）

> 以下题目来源于真实面经、开源面试指南和权威技术博客，按难度分为 **基础（J）/ 进阶（Z）/ 架构（G）** 三级。

## 一、Agent 运行时与状态管理

**1\. 【J】LangGraph 的 Checkpoint 机制是什么？请解释其工作原理。**

- **考察点** ：State 快照、框架级触发（非业务手动保存）、持久化后端选型、thread\_id + checkpoint\_id 恢复机制。

**2\. 【Z】Checkpoint 和普通的状态保存（如手动存 Redis）有什么区别？**

- **考察点** ：架构级事务性快照 vs 业务级变量保存；版本化、幂等性、自动触发时机（step 边界）。

**3\. 【Z】如果 Agent 执行到第 38 步时 Pod 被 K8s 驱逐了，没有 Checkpoint 会发生什么？如何设计恢复机制？**

- **考察点** ：生产级故障场景理解；CheckpointSaver 选型（Redis/PG）；降级策略（Redis 超时后降级 MemorySaver）。

**4\. 【Z】Checkpoint 的触发时机是什么？是每个 Node 还是每个 step？如果 Node 执行到一半进程崩了，能恢复吗？**

- **考察点** ：step 与 Node 的区别；快照的固有粒度限制；子任务拆分或外部事务补偿。

**5\. 【G】设计一个支持 1000 个并发会话的 Agent Runtime，State 持久化层如何选型？MemorySaver、Redis、PostgreSQL 分别适合什么场景？**

- **考察点** ：多租户隔离、并发性能、数据一致性、冷启动延迟、Schema 迁移兼容性。

**6\. 【G】Agent 状态恢复后，如何保证外部副作用的幂等性？（如已经发过的邮件、已经扣的款）**

- **考察点** ：幂等键设计、外部系统查询补偿、结果未知状态的处理。

## 二、Agent 编排与工作流引擎

**7\. 【J】LangChain 和 LangGraph 的核心区别是什么？什么场景下必须用 LangGraph？**

- **考察点** ：LCEL 单向 DAG vs StateGraph 有状态循环；条件边、检查点、HITL。

**8\. 【J】LangGraph 的三要素 State、Node、Edge 分别是什么？条件边（Conditional Edge）解决了什么问题？**

- **考察点** ：状态共享、节点职责、动态路由、ReAct 循环的实现。

**9\. 【Z】ReAct、Plan-and-Execute、Reflexion 三种框架各有什么优劣？分别适合什么场景？**

- **考察点** ：逐步推理 vs 全局规划 vs 自我反思；适用任务复杂度、失败恢复能力。

**10\. 【Z】多 Agent 系统中，Supervisor 模式和 Peer-to-Peer 模式各有什么优缺点？如何选择？**

- **考察点** ：中心化调度瓶颈 vs 去中心化协商复杂度；职责边界、故障隔离。

**11\. 【G】设计一个"编码 Agent + 质控 Agent + 审核 Agent"的三级医疗工作流，如何用 LangGraph 建模状态流转和循环分支？**

- **考察点** ：State Schema 设计、条件边（质控通过/不通过）、interrupt\_before 人工审批、子图嵌套。

**12\. 【G】如何防止多 Agent 协作中的死循环和无限递归？**

- **考察点** ：最大步数限制、状态重复检测、目标完成进度监控、漂移检测。

## 三、工具链、MCP/A2A 与基础设施

**13\. 【J】MCP 和 A2A 协议的定位有什么区别？它们是竞争关系还是互补关系？**

- **考察点** ：Function Calling / MCP / A2A 三层架构；工具标准化 vs Agent 互操作。

**14\. 【Z】MCP 协议中的 Resources、Prompts、Tools 三个概念分别是什么？**

- **考察点** ：上下文资源暴露、可复用提示模板、工具 Schema 定义；模型如何发现与调用。

**15\. 【Z】A2A 协议的 Agent Card 和 Task 状态机分别解决了什么问题？**

- **考察点** ：服务发现（能力声明）、异步任务生命周期（提交→工作→完成）、Agent 微服务化。

**16\. 【G】设计一个公司级 Agent Tool 网关，需要包含哪些核心能力？**

- **考察点** ：统一鉴权、动态注册发现、Schema 校验、限流熔断、多租户隔离、审计日志。

**17\. 【G】当 Agent 需要调用 100+ 个工具时，如何设计工具路由策略，避免每次请求都携带全部工具描述导致 Token 爆炸？**

- **考察点** ：工具分层（领域分类）、意图路由（先分类再选工具）、工具 Embedding 检索、动态加载。

## 四、性能优化与成本治理

**18\. 【J】为什么需要模型路由？直接用一个最强模型不行吗？**

- **考察点** ：成本-质量不对称、长尾分布、延迟优化。

**19\. 【Z】基于意图分级的动态模型路由怎么实现？级联降级（小模型先试，不行再升级）和理想路由相比有什么成本损耗？**

- **考察点** ：轻量级分类器设计、成本矩阵、预算控制、级联降级的额外开销。

**20\. 【Z】提示词压缩（Prompt Compression）有哪些方法？如何在压缩比和效果之间做权衡？**

- **考察点** ：信息保留策略、关键信息保护规则、评测集验证。

**21\. 【Z】LLM 推理中的 Prefix Caching（前缀缓存）是什么？缓存键应该怎么设计？**

- **考察点** ：KV Cache 复用、缓存命中率、缓存一致性、多租户隔离。

**22\. 【G】设计一个"Token 预算管理"系统，支持按医院、按任务类型、按会话三级配额控制，如何实现？**

- **考察点** ：配额模型设计（硬预算/软预算）、Token 使用预测、预扣与返还、超预算降级策略。

**23\. 【G】vLLM 的 PageAttention 为什么能提升推理吞吐量？相比传统预分配有什么优势？**

- **考察点** ：KV Cache 分页管理、内存碎片减少、动态扩缩容、物理不连续逻辑连续。

## 五、安全、沙箱与多租户隔离

**24\. 【J】工具权限、沙箱和人工审批三者如何协同？各自解决什么问题？**

- **考察点** ：三层防御体系；权限判断 → 策略校验 → 沙箱执行 → 人工审批 → 审计日志。

**25\. 【Z】Agent 的安全沙箱需要隔离哪些维度？进程级、网络级、文件系统级分别怎么做？**

- **考察点** ：Docker 隔离、网络策略（无出口）、只读挂载、资源限额（cgroups）、seccomp 系统调用过滤。

**26\. 【Z】多租户场景下，如何防止 Agent A（医院 A）访问到 Agent B（医院 B）的病历数据？**

- **考察点** ：租户 ID 贯穿（请求头/State/缓存键）、数据库行级安全（RLS）、向量库命名空间隔离、Embedding 隔离。

**27\. 【G】设计一个多租户 Agent 运行时架构，要求支持 100 家医院，每家医院的编码规则和数据相互隔离，如何实现？**

- **考察点** ：租户上下文传递（thread\_id 前缀/元数据）、LoRA Adapter 动态加载、知识库隔离、沙箱目录隔离。

## 六、可观测性与治理体系

**28\. 【J】Agent 系统的 Tracing 和普通微服务的 Tracing 有什么区别？Agent 的 Trace 通常是什么结构？**

- **考察点** ：非线性执行路径、LLM 专属 Span 类型、上下文传递（Trace Context）。

**29\. 【Z】OpenTelemetry 在 LLM/Agent 场景下如何落地？LangSmith 的 Trace 和 OTel 是什么关系？**

- **考察点** ：标准化埋点、SDK 自动采集、与现有可观测平台（Datadog/Grafana）集成。

**30\. 【Z】如何监控 Agent 的"上下文漂移"？有哪些检测信号？**

- **考察点** ：目标关联度检测、步骤重复检测、进度停滞检测、人工抽检校准。

**31\. 【G】设计一个 Agent 执行轨迹的审计系统，要求能回放任意一次编码任务的完整决策过程，怎么实现？**

- **考察点** ：Trace 持久化（对象存储）、状态快照版本化、Time-travel 调试、Replay 与 Resume 的区别。

## 七、评估体系与回归验证

**32\. 【J】Agent 的评估和普通 LLM 应用的评估有什么区别？过程指标和结果指标分别有哪些？**

- **考察点** ：任务完成率 vs 文本 BLEU；工具调用准确率、轨迹质量、成本效率。

**33\. 【Z】LLM-as-Judge 有什么系统性偏差？如何缓解？**

- **考察点** ：位置偏差（答案顺序影响）、自我增强偏差（偏好自己生成的风格）、长度偏差；缓解：随机顺序、多裁判、明确 rubric、逃生门。

**34\. 【Z】SWE-bench 跑分高是否代表代码生成 Agent 在真实场景一定好用？为什么？**

- **考察点** ：Benchmark 的局限性（预处理过的上下文、只看测试通过、忽略代码质量）；真实场景需要 A/B 测试。

**35\. 【Z】Prompt 版本升级后，怎么做回归测试？数据集多大够用？**

- **考察点** ：配置即代码、行为漂移检测、黄金评测集、质量门禁（下降 >0.3 分触发回滚）。

**36\. 【G】设计一个三层评估金字塔：单元层、集成层、回归层，分别应该测什么？用什么判定方式？**

- **考察点** ：成本与频率权衡（单元层每次 commit、集成层每次 PR、回归层每次 release）；判定方式从确定性检查到 LLM-Judge 的升级。

## 八、分布式系统与云原生基础

**37\. 【J】Ray 的 Actor 和 Task 有什么区别？Agent 场景中分别适合做什么？**

**39\. 【Z】Kafka/Flink 等流处理经验如何迁移到 Agent 系统？Agent 的"事件驱动架构"怎么设计？**

- **考察点** ：事件溯源（Event Sourcing）、状态机驱动、异步消息队列解耦、背压处理。

**40\. 【G】设计一个高可用的 Agent 推理服务网关，要求支持模型 A/B 测试、灰度发布、流式输出，怎么实现？**

## 九、医疗 Agent 场景设计（结合你的背景）

**41\. 【Z】如何将你之前的小模型 ICD 编码经验，与 LLM Agent 结合？各自承担什么角色？**

- **考察点** ：小模型高召回 + 大模型精排/验证的分层架构；成本与延迟权衡。

- **考察点** ：分层摘要、按需检索（先读结构再深入）、关键片段提取、多 Agent 分片处理。
