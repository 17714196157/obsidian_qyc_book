原创 AI 超车指南 *2026年4月7日 19:26*

前几天，AI大神Andrej Karpathy 分享了一套 `LLM Wiki` 思路，在 AI 圈里传播得可以说是沸沸扬扬、无人不谈，让用Obsidian进行结构化知识管理这个早已不那么新鲜的话题，又焕发了青春。

其实我一直也在使用LLM来辅助知识库的管理，但是基本上还停留在给文章做摘要、打标签的阶段，没有形成一套方法论。可以说，Karpathy的这套LLM Wiki给了大家非常多的启发。与此同时，这个思路本身也一套Agentic工作流，虽然不复杂，但是从头摸索建立还是要花不少时间，甚至有可能会因为过程繁琐、甚至达不到预期效果的种种原因而被劝退。

写这篇文章的初衷就是希望每个小伙伴，以一种最小摩擦的方式，都能体验到AI大神的工作方法，有序而高效的进行知识管理，应用到生活和工作的方方面面。可以视为是LLM Wiki的入门脚手架。

## 为什么这套方法会突然火起来？

Karpathy 在 2026 年 4 月初先发了一条关于 `LLM Knowledge Bases` 的帖子，随后在 2026 年 4 月 4 日把思路整理成一份 GitHub Gist《LLM Wiki》。这份文档里最有启发性的地方，不是某个具体命令，而是他把知识管理这件事重新定义了一遍。

它火的原因，不是因为又多了一个“第二大脑”工具，也不是因为他给出了多复杂的工程方案。恰恰相反，Karpathy 分享的核心，几乎只是一份 idea file：不用先写一套知识库系统，不用先搭一套 RAG 基础设施，也不用先设计一套复杂目录，而是直接让 Agent 和你一起，把一个 Obsidian 仓库逐步“编译”成可查询、可演化、可持续积累的个人 Wiki。

在传统LLM RAG 里，我们通常是把一批文件上传进去，等提问时再让模型去检索相关片段，然后现场拼答案。这样当然能用，但它有一个天然问题：每问一次，模型都像是重新开工一次。知识没有真正沉淀下来，复杂问题也要一遍遍重新拼接。

Karpathy 提出的方式不一样。

它不是让模型在提问时再临时找材料，而是让模型在平时就持续维护一个持久化的 wiki：新资料进来以后，模型不只是做索引，而是会去读、去总结、去更新实体页、概念页、对比页和综合页，把矛盾、关联、上下文都提前整理好。换句话说，知识不是每次从原始文档里重新推导，而是被逐步编译成一个可以不断演化的中间层。

他对这套关系有一句非常形象的概括：

> Obsidian 是 IDE，LLM 是程序员， Wiki 是代码库。

## 这套 LLM Wiki 的最小结构，到底是什么？

Karpathy 在 gist 里把架构拆成了三层：

1. `raw sources` 原始资料层。文章、论文、报告、图片都放在这里，作为事实来源，不直接修改。
2. `wiki` 由 LLM 维护的知识层。这里不是原文堆积，而是被整理过的来源摘要、实体页、概念页、对比页和综合分析页。
3. `schema` 也就是 `CLAUDE.md` 或 `AGENTS.md` 这种规则文件。它告诉 Agent：目录怎么组织、页面怎么写、ingest 时该做什么、查询时该先读什么、健康检查怎么做。

这第三层特别关键。它让 Agent 不再只是一个“会聊天的模型”，而变成一个按照明确规范维护知识系统的执行者。

所以，真正应该先搭的，不是花哨功能，而是一个最小可运行骨架。

## 第一步：先让 Agent 帮你把 Wiki 骨架搭起来

我已经建立了一个名字为：AI-Research的Obsidian Vault，相信用过Obsidian的小伙伴对这部分并不陌生，过程就不再赘述了。接下来就是基于这个仓库来构建Wiki骨架。

这里我给大家总结一个非常高效的技巧，不需要逐个手工建目录结构，而是直接把 Karpathy 的思路喂给 Agent，让大模型利用自身的文件操作底层能力，生成一套面向“AI 前沿研究”的 Wiki 结构，这是最妙的地方，大模型可以根据你的wiki类型和具体要求，生成量身定制知识体系。

目录大致长这样：

```
AI-Research/
├── CLAUDE.md
├── index.md
├── log.md
├── raw/
│   ├── assets/
│   └── google-gemini-2-flash-thinking.md
├── wiki/
│   ├── sources/
│   ├── entities/
│   ├── concepts/
│   ├── comparisons/
│   └── syntheses/
└── templates/
    ├── source-template.md
    ├── entity-template.md
    └── concept-template.md
```

这个结构的好处是非常清楚：

- `raw/` 只存原始资料，不做加工。
- `wiki/` 只存经过模型整理后的知识页面。
- `index.md` 是内容索引，回答问题前先读它，快速定位相关页面。
- `log.md` 是时间线，记录每次 ingest、查询、lint 都做了什么。
- `CLAUDE.md` 是整个系统的运行规则。

看起来只是几个文件夹，但本质上已经把“来源”“知识”“规则”三层分开了。后面所有操作，都是围绕这三层展开。

## 第二步：把文章剪藏进来，让 raw 层稳定运转

Wiki 真正能跑起来，关键不在目录，而在于有没有稳定的资料入口。

这里最顺手的方案，就是用 Obsidian Web Clipper插件（可以在Chrome插件市场下载安装） 把网页直接保存到 `assets/raw/` 。这样做的好处是，原始来源会以 Markdown 形式留在本地，后面不管你是让 Agent 做摘要、抽概念、建实体页，还是回头做人工核查，都有一份不被改写的底稿。

这一步的重点其实只有一个：让你的资料进入系统时就是“可持续处理”的。

很多人的知识管理卡住，不是因为不会记笔记，而是因为来源层太混乱了。有的在浏览器收藏夹，有的在 Notion，有的在 PDF 文件夹，有的只是微信群里看到后没保存。Agent 再强，也架不住输入层是散的。

## 第三步：执行 ingest，把“剪藏”变成“消化吸收”

这是整套工作流最关键的一步。

传统笔记系统里，我们经常停留在“收藏了”这一层。文章存下来了，但并没有变成你自己的知识结构。LLM Wiki 的核心，就是把这一段最费时间、最容易半途而废的体力活，交给 Agent。

实际指令可以非常短：

```
@raw/Effective harnesses for long-running agents.md 请消化吸收这篇文章
```

接下来，Agent 做的不是简单总结，而是把这篇文章拆进整个 Wiki 结构里：

- 新建对应的来源摘要页
- 更新相关实体页
- 更新相关概念页
- 回写 `index.md`
- 记录到 `log.md`

Karpathy 在 gist 里提到，一篇新资料进入系统后，完全可能一次性改动 10 到 15 个页面。这个量，如果靠人手去维护，几乎不可能长期坚持；但如果交给 LLM，它反而正好擅长这种跨页面整理、对齐和回填。

## 第四步：直接提问，让 Agent 基于 Wiki 回答，而不是基于临时记忆现编

当 ingest 跑通以后，这个系统最舒服的体验就出来了。

你不再需要翻原文、回忆“我好像在哪篇文章看过这件事”，而是可以直接把 Wiki 当成一套不断进化的研究底座来用。

比如我这里直接问了一个具体问题：

```
查询笔记，上下文管理中的上下文压缩有什么局限性？为什么它不能确保 agent 长期运行？
```

按照 `CLAUDE.md` 里的规则，Agent 不是直接开始回答，而是先读 `index.md` ，再去读相关 wiki 页面，然后综合多个页面给出带引用的回答。

最后得到的结果，不是单篇文章的摘要，而是建立在多个 Wiki 页面之上的综合答案。

![[公众号文章/assets/5分钟复刻 Andrej Karpathy 的 LLM Wiki：用 Obsidian + Agent 把剪藏、消化、查询连成一个会持续进化的知识系统/173fda21e83f6802e9d2e81a269bdbfe_MD5.webp]]

这件事听起来像小区别，实际上差别很大。

因为这意味着：你问的不是“这篇文章讲了什么”，而是“在我已经沉淀下来的知识系统里，这个问题该怎么解释”。回答的上下文不再只来自单篇材料，而来自你之前已经积累过、整理过、连接过的知识网络。

而且 Karpathy 还强调了一个很实用的点：查询本身也可以继续沉淀。一次好的比较、一次新的分析、一次你在追问中形成的结构化结论，都可以反过来写回 Wiki，成为后续可复用的页面，而不是像普通聊天记录一样就地蒸发。

## 这套方法和 RAG 的区别，到底在哪里？

很多人第一次看到这套方案时，都会问：这不也是一种知识库吗？和 RAG 差在哪？

差别不在“能不能检索”，而在“知识是否会累积”。

RAG 的典型逻辑是：

1. 资料先存着
2. 提问时临时检索 chunk
3. 模型现场拼装答案

LLM Wiki 的逻辑则是：

1. 新资料进来先被系统性消化
2. 消化结果被写进结构化页面
3. 页面之间提前建立链接、指出矛盾、形成摘要
4. 提问时优先查询这层已经被整理过的知识

也就是说，RAG 更像“每次临时翻档案”；LLM Wiki 更像“持续整理档案，并把整理结果留下来”。

Karpathy 在 gist 里提到，至少在中等规模下，这种方式非常实用。大约 `~100` 个来源、几百个页面的规模，单靠 `index.md` 作为目录入口，就已经能工作得很好，甚至不一定需要一开始就上 embedding 检索或复杂基础设施。

这点非常重要，因为它把门槛降下来了。

大多数人不是缺少一个更高级的知识库架构，而是缺少一条今天就能启动、明天还能继续用的路径。LLM Wiki 给出的，就是这样一条路径。

## 为什么它特别适合研究型学习和内容生产？

因为它把过去三件容易断掉的事接到了一起：

1. 检藏 把网页、论文、报告稳定收进 `raw/`
2. 消化 让 Agent 把资料拆成来源页、概念页、实体页、综合页
3. 利用 后续写文章、做选题、回答问题、做对比分析时，直接站在 Wiki 上继续推进

过去我们的常见问题是：收藏很多，吸收很少；看过很多，调用很难；写作时又重新找资料，像从零开始。

而当你把 Agent 放进这条链路里以后，知识就不再只是“存过”，而是“整理过、链接过、可以继续调用过”。

这也是为什么我觉得，它特别适合下面几类人：

- 长期跟踪某个主题的研究者
- 需要持续积累选题与素材的内容创作者
- 想把论文、报告、文章沉淀成可复用知识资产的人
- 想做团队内部研究 Wiki，但又不想让人工维护变成负担的小团队

## 两个非常实用的小技巧

### 1\. 把图片下载到本地，不要只依赖网页 URL

这一点 Karpathy 在 gist 里专门提了，我自己也非常认同。

如果图片只是在网页里通过远程 URL 引用，Obsidian 虽然能显示，但并不稳定。原网页改版、失效、反盗链，都会导致以后再读时图片缺失。更关键的是，LLM 后续如果要分析图片内容，也更适合直接访问本地附件。

所以建议在 Obsidian 里把附件目录固定到类似 `raw/assets/` 的位置。

![[公众号文章/assets/5分钟复刻 Andrej Karpathy 的 LLM Wiki：用 Obsidian + Agent 把剪藏、消化、查询连成一个会持续进化的知识系统/59ca4231d6b62f935a280e18c8f223c3_MD5.webp]]

再给“Download attachments for current file”绑定一个快捷键。这样每次剪藏完网页后，都可以把图片一并落地。

![[公众号文章/assets/5分钟复刻 Andrej Karpathy 的 LLM Wiki：用 Obsidian + Agent 把剪藏、消化、查询连成一个会持续进化的知识系统/511b9301df8e668a12c7000aebfdc85d_MD5.webp]]

我自己还会再多做一步，建议大家也能借鉴：让 Agent 在 ingest 时顺手把图片改成有意义的名字。这样后面无论是检索、引用，还是让模型理解图片含义，都会顺很多，不然这些从网上下载的图片名称就是一些无意义的标识符，不利于后续的使用。

### 2\. 不要一开始就追求完美 schema，让它边用边长

Karpathy 在 gist 里其实也反复强调：这不是一套唯一正确的实现方案，而是一种 pattern。

所以最好的方式不是一开始写一份巨复杂的 `CLAUDE.md` ，而是先跑起来，然后随着使用逐步演化规则。比如：

- 哪些页面必须带 YAML frontmatter
- 来源页和概念页分别用什么模板
- 查询回答要不要强制引用页面
- lint 时重点检查哪些问题

一套真正能长期使用的知识系统，不是设计出来的，而是在使用中被迭代出来的。

## 最后：这套方法最打动我的，不是“能建 Wiki”，而是“能让知识开始复利”

过去我们做知识管理，最容易卡在两个地方。

第一是收集之后没整理，资料越堆越多。

第二是整理之后没复用，笔记写完就躺在那里。

Karpathy 这套 LLM Wiki 给出了一条很现实的路线：让 Agent 接管那些最枯燥、最繁琐、最容易让人半途放弃的维护工作，人负责选资料、提问题、做判断，模型负责整理、交叉引用、回填索引、维护一致性。

这不是在“用 AI 代替思考”，而是在把那些本来最不值得你亲自消耗精力的体力劳动，从知识工作中剥离出去。

如果你也想搭一个自己的研究型知识库，我的建议不是先追求大而全，而是先照着这篇文章做一遍最小闭环：

1. 建一个 Obsidian 仓库
2. 让 Agent 生成 Wiki 骨架
3. 剪藏一篇文章到 `raw/`
4. 执行一次 ingest
5. 基于 Wiki 问第一个问题

只要这 5 步走通，你的知识系统就已经不是“资料仓库”了，而是一个会随着输入不断进化的工作台。
