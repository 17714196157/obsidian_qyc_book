## 概述

RAG 准确率从 60% 提升到 85% 的工业级方法论：先分层诊断定位问题（召回率 vs 忠实度），再依次优化数据切分、Query 处理、混合检索和策略路由，最终形成可迭代的优化闭环。

> [!abstract] 一句话总结
> 四句口诀：切分顺着语义走、扩写带防幻觉校验、多路打分统一排序、召回忠实两把尺——问题出在哪层测哪层。

---

## 一、问题定位：先诊断再开方

> [!important] 核心原则
> **不盲目调参**，先明确问题根源，再对症下药。

### 两个关键指标

| 指标 | 评估环节 | 说明 | 低值意味着 |
|------|---------|------|-----------|
| **上下文召回率** | 检索环节 | 信息是否被正确检索到 | `embedding` 模型或数据切分策略有问题 |
| **忠实度** | 生成环节 | 答案是否严格基于检索内容 | 模型存在幻觉（hallucination） |

```
问题定位决策树：

准确率不达标？
    │
    ├── 召回率低？──→ 优化 embedding / 切分策略 / 检索
    │
    └── 忠实度低？──→ 优化 prompt 约束 / 更换模型 / 加防幻觉机制
```

## 二、数据切分优化：语义感知动态切分

### 传统方法的缺陷

固定 token 切分（如 256/512）会导致**关键信息被腰斩**，跨边界的语义无法保留。

### 工业级解决方案

| 策略 | 做法 | 作用 |
|------|------|------|
| **语义感知动态切分** | 在句子/段落边界自然断开 | 保持语义完整性 |
| **重叠窗口** | 相邻 chunk 保留 **10%-20%** 重叠 | 防止关键信息被截断在边界处 |

> [!tip] 效果数据
> 粗糙切分场景下，改用语义切分可提升 **10-15%** 准确率。

```
固定切分 256-token ❌         语义切分 ✓
┌──────────────────┐          ┌────────────────┐
│ ...到一半就被切断了 │          │ 完整句子/段落     │
│ 剩下的在下个chunk  │          │ 完整句子/段落     │
│ 上下文丢失         │          │ 相邻重叠10-20%    │
└──────────────────┘          └────────────────┘
                              每个chunk = 完整语义单元
```

## 三、Query 扩写与校验：防幻觉带路

### 问题

用户提问往往口语化、缺上下文（如"那个怎么弄"），直接检索命中率低。

### 解决方案

**Step 1：大模型扩写** → 将模糊查询转化为规范化检索语句

**Step 2：防幻觉校验** → 防止扩写偏离原意

```
原始 query ──→ 大模型扩写 ──→ 计算 embedding 余弦相似度
                                    │
                          ┌─────────┴─────────┐
                          │                   │
                      ≥ 阈值               < 阈值
                          │                   │
                          ▼                   ▼
                    使用扩写 query       回退到原始 query
```

**阈值设置参考：**

| 场景 | 余弦相似度阈值 | 说明 |
|------|---------------|------|
| **敏感场景** | 0.8 - 1.0 | 金融、医疗等不容错的领域 |
| **开放域** | 0.65 - 0.7 | 通用问答，允许适度泛化 |

> [!warning] 偏离案例
> 用户问"Python 怎么连数据库"，扩写误加了 MySQL 限定条件，导致检索方向完全跑偏。必须靠余弦相似度拦截。

## 四、混合检索与重排序：多路融合

### 向量检索 vs 关键词检索

| 类型 | 优势 | 劣势 |
|------|------|------|
| **向量检索** | 语义泛化能力强 | 精确匹配弱（专有名词、版本号等） |
| **关键词检索**（BM25） | 精确匹配强 | 语义泛化弱（同义词、改写无法命中） |

### 分数融合方案

> [!important] 核心方法
> 使用 **LambdaMART** 排序学习模型统一处理不同量纲的分数（BM25、余弦相似度等）。

| 特点 | 说明 |
|------|------|
| **可解释性强** | 特征权重透明，可调试 |
| **推理延迟低** | 树模型推理快，适合在线服务 |
| **量纲统一** | BM25 分数和余弦相似度不在同一尺度，LambdaMART 自动学习最优组合 |

## 五、策略路由：延迟与精度平衡

> [!tip] 核心思路
> 不是所有查询都需要重型管线，按复杂度分级处理。

```
用户 Query
    │
    ▼
┌──────────────────┐
│ 轻量分类器判断复杂度 │
└────────┬─────────┘
         │
    ┌────┴────┐
    │         │
 简单查询    复杂查询
    │         │
    ▼         ▼
纯向量检索    混合检索 + Rerank
跳过重排序    全链路
    │         │
    └────┬────┘
         │
         ▼
    返回结果
```

| 查询类型 | 管线 | 延迟 | 精度 |
|---------|------|------|------|
| **简单查询** | 纯向量检索 + 跳过重排序 | 低 | 够用 |
| **复杂查询** | 混合检索 + LambdaMART 重排序 | 较高 | 有保障 |

> [!note] 效果
> 整体延迟可控，复杂问题精度有保障。大部分查询走轻量路径，少量复杂查询走全链路。

## 六、持续迭代与验证：双指标闭环

> [!warning] 关键纪律
> 每次优化后**必须同时验证两个指标**，避免"按下葫芦浮起瓢"。

```
每次优化 ──→ 验证召回率 ──→ 验证忠实度
                │                  │
           检索质量是否提升？   生成质量是否下降？
                │                  │
           ✓ 通过             ✓ 通过
                │                  │
                └────────┬─────────┘
                         │
                         ▼
                    优化有效，合入
```

| 操作 | 验证指标 | 防止 |
|------|---------|------|
| 改切分策略 | 召回率 | 语义完整性没提升反而下降 |
| 加 Query 扩写 | 召回率 + 忠实度 | 扩写引入偏差导致生成偏离原文 |
| 换检索/重排模型 | 召回率 | 重排引入偏见 |
| 改 Prompt/模型 | 忠实度 | 模型幻觉增加 |

## 七、关键口诀：四句核心方法论

> [!quote] RAG 优化四句诀
> 1. **切分要顺着语义走**，别按字数硬切
> 2. **扩写要带校验**，别让幻觉带偏检索
> 3. **多路打分要统一**，排序模型来兜底
> 4. **召回忠实两把尺**，问题出在哪层测哪层
