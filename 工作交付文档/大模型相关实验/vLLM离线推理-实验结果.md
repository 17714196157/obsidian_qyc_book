# vLLM 离线批处理笔记

**日期：** 2026-05-11

## 维度对比：离线推理（LLM类） vs 在线服务（vllm serve）

| 维度 | 离线推理（LLM类） | 在线服务（vllm serve） |
|------|-------------------|------------------------|
| 调用方式 | Python 函数调用 | HTTP API（OpenAI 兼容） |
| 网络开销 | 零 | 每次请求都有序列化/反序列化 |
| 批量处理 | 原生支持，自动 batch | 需要客户端自己管理并发 |
| 延迟 | 仅模型推理时间 | 模型推理 + 网络传输 + 请求排队 |
| 吞吐量 | 高（GPU 利用率拉满） | 受限于服务层调度 |
| 适用场景 | 批量数据处理 | 实时对话、API 服务 |
| 部署复杂度 | 一个 Python 脚本 | 需要管理服务进程、端口、监控 |

## 请求示例 —— 手术细化

```
角色：user
content：
## 角色
你是一位医学专家。

## 任务
请按照说明，分析手术记录的描述，执行以下任务。
任务1：从“备选手术名称”中，选择最合适的一个手术名称，并返回该手术名称；如果没有合适的，则返回"无法判断"。
说明：
1、要根据手术记录中给出的事实证据进行判断，绝对不可以做没有依据的推测。应以手术过程描述为准，手术记录中的手术名称可能不准确。
2、从“备选手术名称"中选择，不要生成。

## 输出要求
1. 输出格式：json
2. 字段定义：
   - answer：包含所有输出结果。
   - reasoning：说明判断理由。

严格输出JSON格式，不要添加任何解释、markdown标记或额外文字：
示例1：输出一个结果
{"answer":["手术名称1"], "reasoning":["填写理由"]}
示例2：输出多个结果
{"answer":["手术名称1", "手术名称2"], "reasoning":["填写理由"]}
示例3：无法判断的情况
{"answer":["无法判断"], "reasoning":["填写理由"]}

备选手术:
### XXXX
## 手术记录:
XXXXX
检查报告：XXXXX
```

## 实验结论

> 在 vLLM serve 模式下，并发数超过 256 后进入 **“内卷区”** —— 请求互相抢占 GPU，单请求速度暴跌，总吞吐不再提升。  
> 对于医疗日志批量处理任务，**128 ~ 256 并发** 是性价比最优区间；  
> 若追求极致效率，应迁移到 **原生离线 batch 模式**。
