# 大模型讨论实验的合理性
✅ 核心结论
**一卡部署2个模型在技术上是可行的**——50个请求100%成功，无OOM，两个模型都能正常响应。
### 🔴 风险点分析

| 风险项                 | 严重程度  | 说明                         |
| ------------------- | ----- | -------------------------- |
| **GPU 2 显存利用率100%** | ⚠️ 高  | `0.8 + 0.2 = 1.0`，没有任何缓冲空间 |
| **缺乏压力测试**          | ⚠️ 中高 | 并发仅8，未测试高并发、长序列、突发流量场景     |
| **未测试边界情况**         | ⚠️ 中  | 未验证显存碎片、模型加载顺序、热启动等        |

### 🔍 具体风险拆解

 🔴 风险1：CUDA内存池"预分配抢占"，显存分配是"硬上限"，不是"实际占用"**
```plain
vLLM启动时：
  进程A (QwQ): 申请 38.4GB → CUDA Memory Pool A
  进程B (Qwen): 申请 9.6GB  → CUDA Memory Pool B
                ↓
        两个Pool在同一块48GB物理显存上
```
**危险点**：CUDA内存池是**贪婪分配**的。如果进程A的KV Cache动态增长（长序列进来），它会尝试从自己的Pool里拿，但如果Pool不够了，不会自动去"抢"进程B的Pool——而是直接OOM。

🔴 风险2：KV Cache动态膨胀

|模型|max-model-len|当前测试序列长度|潜在膨胀空间|
|:--|:--|:--|:--|
|QwQ|10000|~200 tokens|**50倍膨胀空间**|
|Qwen|512|~200 tokens|2.5倍膨胀空间|

QwQ的KV Cache如果碰到长上下文，膨胀是最致命的。

🔴 风险3：并发 peaks 时的"共振OOM"
```plain
时间线：
t1: QwQ收到10个长序列请求 → KV Cache占用 ↑↑
t2: 同时Qwen收到20个短序列请求 → KV Cache占用 ↑
t3: 两个进程同时申请新block → 物理显存不足 → OOM
```

🔴 风险4：显存碎片
两个进程各自管理自己的block table，长期运行后会产生碎片，导致"总空闲显存够，但连续块不够"的分配失败。

| 建议                                                                  | 优先级   |
| ------------------------------------------------------------------- | ----- |
| **增加显存缓冲**：GPU 2上两个模型的`gpu-memory-utilization`之和控制在 **0.85-0.9** 以下 | 🔴 必须 |
| **做压力测试**：长序列（8k+）、高并发（32+）、突发流量                                    | 🔴 必须 |
| **监控显存碎片**：用`nvidia-smi`观察实际占用，而不仅是逻辑分配                             | 🟡 重要 |
| **考虑MIG或隔离**：如果L20支持MIG，物理隔离比逻辑隔离更安全                                | 🟡 重要 |
| **设置OOM保护**：vLLM的`--swap-space`或`--num-gpu-blocks-override`         | 🟡 重要 |

> **实验证明了"能跑"，但没证明"能稳跑"。** 你的担心有道理——这个配置在轻负载下没问题，但在生产环境的长序列、高并发、突发流量场景下，OOM风险很高。建议加缓冲、做压测、上监控，再考虑上线。


# 推荐实验思路

## 场景分析
从截图可以看到关键配置：
- **QWQ-32B-FP8**（2卡并行）：`gpu-memory-utilization=0.8`，占用 GPU 1,2
- **Qwen2.5-0.5B**（单卡）：`gpu-memory-utilization=0.2`，占用 GPU 2

**核心冲突**：两个 vLLM 进程都在 **GPU 2** 上运行，各自预分配了 `0.8 + 0.2 = 100%` 的显存池。

## 风险分析

| 风险 | 机制 | 后果 |
|------|------|------|
| **OOM 崩溃** | 两个进程同时尝试从各自池中分配 KV Cache，物理显存总和 > 100% | CUDA OOM，进程崩溃 |
| **内存碎片/分配失败** | CUDA 内存分配器面对两个大池的交错分配请求 | `cudaMalloc` 失败，请求排队或报错 |
| **性能抖动** | 显存竞争导致频繁的内存换页/重分配 | P99 延迟飙升，吞吐量下降 |
| **静默数据损坏** | 极端情况下驱动层行为未定义 | 模型输出异常（罕见但致命） |

### 实验一：压力并发下的 OOM 触发实验
**目的**：验证双进程同卡时是否会触发 OOM
```bash
# 1. 先启动 qwen2.5-0.5b（0.2 util，GPU 2）
CUDA_VISIBLE_DEVICES=2 vllm serve Qwen/Qwen2.5-0.5B-Instruct \
  --served-model-name qwen-small \
  --port 8104 \
  --tensor-parallel-size 1 \
  --gpu-memory-utilization 0.2 \
  --max-model-len 512 &

# 2. 再启动 qwq-32b-fp8（0.8 util，包含 GPU 2）
CUDA_VISIBLE_DEVICES=1,2 vllm serve QwQ-32B-FP8-dynamic \
  --served-model-name qwq \
  --port 8102 \
  --tensor-parallel-size 2 \
  --gpu-memory-utilization 0.8 \
  --max-model-len 10000 &

# 3. 同时向两个服务发送持续并发请求
# 使用不同的 max_tokens 来逐步增大 KV Cache 占用
```

**观测指标**：
```bash
# 实时监控物理显存（不是 vLLM 报告的池大小）
watch -n 0.5 'nvidia-smi --query-gpu=memory.used,memory.free,utilization.memory --format=csv -i 2'

# 监控进程日志中的 OOM 错误
tail -f /var/log/qwq-32b-fp8.log /var/log/qwen25-0.5b-instruct.log | grep -i "out of memory\|OOM\|cuda\|memory"
```

**预期结果**：
- 如果总请求 KV Cache 需求 < 物理显存：正常运行（但池是"虚"的）
- 如果总需求 > 物理显存：**后分配者**（通常是 qwen-small 或 qwq 的某张卡）触发 `CUDA out of memory`

### 实验二：显存竞争下的性能退化实验

**目的**：量化同卡竞争对延迟和吞吐的影响

```python
# benchmark_dual.py
import asyncio, time, statistics
from openai import AsyncOpenAI

async def benchmark(client, model, prompt_len, max_tokens, concurrency, duration_sec):
    """持续压测，记录延迟分布"""
    latencies = []
    start = time.time()
    
    async def one_request():
        t0 = time.time()
        await client.chat.completions.create(
            model=model,
            messages=[{"role": "user", "content": "x" * prompt_len}],
            max_tokens=max_tokens,
            temperature=0.7
        )
        return time.time() - t0
    
    # 持续并发
    while time.time() - start < duration_sec:
        tasks = [one_request() for _ in range(concurrency)]
        batch = await asyncio.gather(*tasks, return_exceptions=True)
        for r in batch:
            if isinstance(r, Exception):
                latencies.append(("ERROR", str(r)))
            else:
                latencies.append(("OK", r))
    
    return latencies

# 测试矩阵
# 1. 仅 qwq 服务（独占 GPU 2，作为 baseline）
# 2. 仅 qwen 服务（独占 GPU 2，作为 baseline）  
# 3. 两者同时运行 + 同时压测（竞争场景）
```

**关键对比**：
| 场景 | QWQ P99 延迟 | Qwen P99 延迟 | 错误率 |
|------|-------------|-------------|--------|
| 独占 GPU 2 | baseline | baseline | 0% |
| 共享 GPU 2 | ? | ? | ? |

### 实验三：显存池"虚占"验证实验

**目的**：证明 `gpu-memory-utilization` 是预分配上限，不是实际占用

```bash
# 启动后立刻查看（还没收到请求时）
nvidia-smi -i 2

# 你会看到：
# vLLM 内部报告的 allocated_memory = 0.8 * total_GB（对 qwq）
# vLLM 内部报告的 allocated_memory = 0.2 * total_GB（对 qwen）
# 但 nvidia-smi 显示的 used_memory 可能远小于两者之和
# 因为 CUDA 内存池是"预留"而非"实际分配每一字节"
```

**更精确的验证**：
```python
# 通过 pynvml 获取实际分配 vs 池大小
import pynvml
pynvml.nvmlInit()
handle = pynvml.nvmlDeviceGetHandleByIndex(2)

# 实际已分配显存
info = pynvml.nvmlDeviceGetMemoryInfo(handle)
actual_used = info.used / 1024**3

# 对比 vLLM 的 /metrics 端点暴露的
# vllm:gpu_cache_usage_perc * pool_size
```

# 回复领导："想拉满显存和利用率"

| 方案                | 显存利用率  | GPU利用率 | 风险          | 建议                  |
| ----------------- | ------ | ------ | ----------- | ------------------- |
| **当前方案**（共享GPU 2） | 100%   | 中      | 🔴 OOM、服务中断 | 仅做PoC，不上生产          |
| **方案A：调整水位**      | 85-90% | 高      | 🟡 可控       | **推荐短期方案**          |
| **方案B：MIG物理隔离**   | 80-85% | 高      | 🟢 低        | **推荐长期方案**（如果L20支持） |
| **方案C：动态调度**      | 动态90%+ | 高      | 🟡 需开发      | 中长期规划               |
**替代方案**
**方案A：保守水位（立即实施）**
```bash
# 调整启动参数
# QwQ: gpu-memory-utilization 0.75 (从0.8降)
# Qwen: gpu-memory-utilization 0.15 (从0.2降)
# GPU 2合计: 0.9，留10%缓冲
```

> "这样只牺牲了10%的理论上限，但OOM风险大幅降低。同时把Qwen的max-model-len从512提升到2048，实用性更强。"

**方案B：MIG隔离（如果硬件支持）**

> "L20支持MIG的话，可以把一张卡切成两个实例，物理隔离，互不影响。利用率也能到80%以上，但稳定性高很多。"

```bash
如何查看你的 GPU 是否支持 MIG
# 方法1：查看 nvidia-smi 输出中是否有 MIG M. 列
nvidia-smi

# 方法2：详细查询 MIG 模式状态
nvidia-smi -q | grep -i "mig"

# 方法3：查看支持的 MIG 配置（如果支持的话）
nvidia-smi mig -lgip

# 方法4：查询 GPU 详细信息
nvidia-smi --query-gpu=pci.bus_id,name,mig.mode.current --format=csv
```
**如果 L20 不支持 MIG**，执行 `nvidia-smi mig` 相关命令会报错，或者 `nvidia-smi -q` 输出中**没有 MIG 相关字段**。

**方案C：动态调度（中长期）**

> "调研一下vLLM的`--num-gpu-blocks-override`（用于**手动覆盖 KV Cache 的 GPU block 数量**的启动参数）或者集成K8s的GPU调度，根据实时负载动态分配，而不是启动时固定死。"
